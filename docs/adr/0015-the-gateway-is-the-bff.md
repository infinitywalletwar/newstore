# The gateway is the backend-for-frontend

## Status

Accepted

## Date

2026-11-13

## Context

From Phase 1b a browser signs in and buys a copy. The browser must call Catalog, Inventory and Orders with the user's identity, and the services check an access token from Keycloak (ADR 0012). The question is who holds that token: the browser app or a server.

## Decision

The YARP gateway is the backend-for-frontend (BFF). It signs the browser in to Keycloak as the confidential client `gateway` (authorization code flow with PKCE), keeps the tokens in a server-side session, and gives the browser only an HttpOnly cookie, `newstore-session`. It forwards `/api/*` calls to the services with the user's access token in `Authorization: Bearer`, and removes the `Cookie` header on the way. Duende's `AddOpenIdConnectAccessTokenManagement()` refreshes the access token before it expires.

- **Why a BFF.** [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html) (BCP 212, OAuth 2.0 for Browser-Based Applications) says in section 6: "The patterns in this section are presented in decreasing order of security." Its section 6.1.4.3 says of the BFF: "This architecture is strongly recommended for business applications, sensitive applications, and applications that handle personal data." A shop that takes payments is such an application.
- **The session is a Redis ticket.** `RedisTicketStore` (an `ITicketStore`) keeps the claims and tokens in Redis, and the cookie carries only a key. Data Protection keys are in Redis too (`SetApplicationName("newstore-gateway")`), so a restart or a second gateway instance reads the same cookies. A Redis failure while reading a ticket is logged and the request is anonymous.
- **The cookie: `HttpOnly`, `SameSite=Strict`, no `Secure` and no `__Host-` prefix until Phase 4.** RFC 10017 section 6.1.3.2 says: "The BFF SHOULD enable the `SameSite=Strict` flag for its cookies." The same section says "The BFF MUST enable the `Secure` flag for its cookies" and "The BFF MUST enable the `HttpOnly` flag for its cookies", and asks for a `__Host-` name prefix. We follow `Strict` and `HttpOnly`. We do not set `Secure` or the prefix because the local stack has no HTTPS until Phase 4, and MDN says "Insecure sites (with `http:` in the URL) can't set cookies with the `Secure` attribute" ([MDN, Block access to your cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)). This is a known deviation from a MUST, and Phase 4 closes it.
- **Why `Strict` works for this app.** [RFC 6265bis](https://httpwg.org/http-extensions/draft-ietf-httpbis-rfc6265bis.html) (section 5.6.7.1) says: "Same-site cookies in "Strict" enforcement mode will not be sent along with top-level navigations which are triggered from a cross-site document context." So when the browser comes back from Keycloak (or from FakePay later) on another site, that one navigation arrives without the session cookie. That request only loads the static `index.html`. The app's own `fetch` calls to `/auth/user` and `/api/*` start from the gateway's own page, so they are same-site and carry the cookie. The sign-out link is a navigation from the app's own page too. `Lax` would also send the cookie on a cross-site top-level `GET`, which a state-changing `GET` such as `/auth/logout` must not rely on: it needs the session's `sid` anyway. We found no flow of this app that `Strict` breaks. That is reasoning from the two sources above, not a browser run: the real-browser check is Task 9's Playwright run in CI.
- **Locally the difference cannot show.** [web.dev](https://web.dev/articles/same-site-same-origin) says "Websites that have the same scheme and the same eTLD+1 are considered "same-site"" and labels a different port "Same-site: different ports don't matter." So `http://localhost:8100` (gateway) and `http://localhost:8180` (Keycloak) are one site, and `Strict` and `Lax` behave the same on the Mac (web.dev doesn't mention localhost: this is applying its rule, not something we ran in a browser). RFC 6265 section 8.5 adds "Cookies do not provide isolation by port", so the browser also sends `newstore-session` to every service on `localhost`.
- **A custom header is the CSRF defence, `SameSite` is only a layer.** A request that the cookie authenticates, to `/api/*` or `/auth/user`, must carry `X-CSRF: 1`, else it is a 403 problem `csrf` and is not forwarded. Bearer and anonymous requests need no header, because they have no cookie to abuse. RFC 10017 asks for this ("the BFF SHOULD require that the browser-based application includes a custom request header", section 6.1.3.3.2, as quoted in roadmap topic 09). `SameSite` does not cover requests from another origin on the same site (see above), and a `GET` that Lax allows.
- **The OpenID Connect handler's own cookies are `Lax`, `SameAsRequest` and `ResponseMode = query` until Phase 4.** The API reference says the correlation cookie's "SameSite defaults to None" and its "SecurePolicy defaults to Always" ([CorrelationCookie](https://learn.microsoft.com/dotnet/api/microsoft.aspnetcore.authentication.remoteauthenticationoptions.correlationcookie?view=aspnetcore-10.0)); the nonce cookie has the same two defaults ([NonceCookie](https://learn.microsoft.com/dotnet/api/microsoft.aspnetcore.authentication.openidconnect.openidconnectoptions.noncecookie?view=aspnetcore-10.0)). A `SameSite=None` cookie needs `Secure` (MDN: "if `SameSite=None` is set then the `Secure` attribute must also be set"), which plain HTTP is not, so a browser drops them and the callback fails correlation. `Lax` is sent on a cross-site top-level navigation that uses a safe method (RFC 6265bis, section 4.1.2.7: "cross-site top-level navigations", with the safe-method condition in 5.6.7.1). The default response mode, `form_post`, brings the browser back with a POST, which is not a safe method (reasoning from those two sentences), so the code comes back in the query string instead. Phase 4 restores `Secure`; whether to go back to `form_post` is then open.
- **Sign-out.** `/auth/logout?sid=` checks the session's `sid` claim and answers 400 if it differs, so another site cannot sign the user out with a link. It then signs out of the cookie scheme (this deletes the Redis ticket) and of Keycloak (with `id_token_hint`). The handler's default post-logout address, `/signout-callback-oidc`, is not among the realm client's post-logout redirect URIs and Keycloak answered "Invalid redirect uri" in a test, so the gateway asks Keycloak to return to `/` directly.
- **A session that cannot refresh ends.** When Duende cannot refresh the access token, the gateway signs the cookie scheme out and answers 401 problem `session-expired`. The app shows "Your session ended".
- **A challenge on `/api/*` is a 401, never a redirect.** .NET 10's cookie handler answers 401 instead of a redirect only for endpoints it recognises as APIs. We removed our override once and ran `Anonymous_call_to_a_signed_in_route_is_401_not_a_redirect`: a YARP route got `302 Found`. So the cookie scheme's `OnRedirectToLogin` writes the 401 problem for `/api/*`.
- **Every route is listed.** An unknown `/api/*` path is a 404 problem. A service's `/health/ready` or `/openapi/v1.json`, and endpoints that only other services call (reservations, the owner endpoint), are not routed (`Internal_paths_are_not_routed`).

## Alternatives considered

- **The SPA holds the tokens, with PKCE.** This was the README's design before Phase 1b. The tokens are then readable by any script on the page, and RFC 10017 ranks the browser-only pattern below the BFF ("in decreasing order of security", section 6). It is the cheapest to run: no session store, no CSRF. We chose the BFF because the app handles payments.
- **A token-mediating backend.** The backend does the sign-in and gives the browser app an access token, which the app uses to call the services itself. RFC 10017 lists it between the two other patterns (as summarised in roadmap topic 09; the mechanics here are not checked against the RFC text). The browser app then holds an access token, so a stolen page script can read it (reasoning).
- **Tokens inside the cookie (client-side session).** RFC 10017 section 6.1.2.3 says "Client-side sessions push all data to the browser in a signed, and optionally encrypted, object." We measured a real ticket from the local Keycloak: 4733 bytes serialized, with the id, access and refresh tokens, before encryption and base64 grow it. [RFC 6265 section 6.1](https://www.rfc-editor.org/rfc/rfc6265.html) asks user agents to support "At least 4096 bytes per cookie", so it is over that guaranteed size (what each browser really accepts: not verified). A cookie also cannot be revoked on the server: the copy in the browser stays valid until it expires.
- **Server-side session in Redis (chosen) and the RFC's warning.** Section 6.1.2.3 says "Server-side sessions expose only a session identifier and keep all data on the server", and "Given these downsides, using server-side sessions with a BFF is only recommended in small-scale scenarios." The downsides it names are sticky sessions or session replication. They do not apply here: every gateway instance reads the same Redis, so there is no per-instance state. What remains is a Redis read on each signed-in request and Redis as a dependency. This fits at newstore's size. It would stop fitting if the session reads had to cross regions or Redis became the bottleneck, and then a client-side session with short-lived tokens is the alternative.
- **ASP.NET Core antiforgery tokens instead of the header.** RFC 10017 section 6.1.3.3.3 says they are "not necessarily recommended over the CORS approach" (roadmap topic 09 quotes it). A YARP route binds no form, so nothing would act on the validation result (reasoning, in topic 09).

## Consequences

- **Costs:** a session store (Redis) the gateway depends on for signed-in calls; the CSRF header every cookie call must send; the gateway is a stateful part of the login path. Anonymous browsing does not need Redis (`Anonymous_browsing_works_when_redis_is_down`) and the readiness check reports `Degraded`.
- **Tickets in Redis hold the tokens unencrypted.** Redis is only on the private Compose network, and its keys are the cookie's only content. Encrypting the ticket before storing it would add little while the Data Protection keys sit in the same Redis.
- **Known gap: sign-out does not revoke the refresh token explicitly.** [Keycloak's logout endpoint](https://www.keycloak.org/securing-apps/oidc-layers) "logs out the authenticated user": redirecting the user agent "causes the active user session to be logged out". The page does not say what happens to the session's refresh tokens or access tokens, and revoking the refresh token is not part of this task. We saw that after an administrator ended a user's sessions through the admin API, a refresh failed (`Expired_session_is_401_session_expired`), but we did not test the logout redirect itself. An access token already issued stays valid until it expires (300 seconds from the local Keycloak, ADR 0012). Revoking the refresh token at sign-out would close it.
- **Plain HTTP until Phase 4.** No `Secure` flag, no `__Host-` prefix, and the handler cookies are `Lax` with `SameAsRequest`. Phase 4 sets `Secure` and the prefix and decides on `form_post`. Until then the stack is local-only (AGENTS.md).
- **`Strict` is checked in a real browser only by Task 9.** If it breaks a flow there, switch to `Lax` and write the reason here.
- Adding a service route is a line in `ProxyExtensions`, plus a test that the path is forwarded. A path nobody lists stays internal.
