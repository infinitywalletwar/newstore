# Payments is a service, and the provider is behind an interface

## Status

Accepted

## Date

2026-11-13

## Context

Story C-2: a buyer pays on a provider's hosted page, and "paying twice, or a payment provider retrying its callback, never charges twice or assigns two copies". A payment that succeeds after the reservation's hold ran out must be refunded (C-2, and the README's Decisions).

Three forces shape the design:

- The provider answers in two ways: a reply to our call, and a webhook later. Either can repeat or get lost.
- Phase 7 moves to Stripe test mode. Nothing outside the provider code should change.
- Until then, tests and the local stack need a provider that is fast, offline and under our control.

## Decision

1. **Payments is its own service,** with its own database (`payments`: `payment_attempts`, `provider_events`, the outbox and the inbox). The owner chose this on 2026-11-08. Payments talks to the provider and owns the idempotency rules around it. Orders asks Payments for a payment (`POST /payments`, only Orders' client token passes the policy) and reacts to `PaymentSucceeded`, `PaymentFailed` and `PaymentRefunded` on one topic, `payments.payments`, keyed by order id.
2. **The provider sits behind `IPaymentProvider`:** `CreateSessionAsync`, `RefundAsync` and `ReadWebhook`. The rest of Payments sees only `ProviderSession` and `ProviderEvent`. FakePay implements it now; a Stripe implementation replaces `FakePayProvider` in Phase 7, and its webhook parsing and signature check live in that class alone.
3. **FakePay is a separate small app** (`src/Fakes/FakePay`, state in memory, no database, no outbox), so the integration is a real HTTP integration. It copies the parts of Stripe's Checkout that matter here:
   - A session is created with an `Idempotency-Key`; the same key returns the same session. Stripe: "For API v1, Stripe saves the status code and body of the first request made with a given idempotency key … Retries with the same key return the saved response" ([Idempotent requests](https://docs.stripe.com/api/idempotent_requests)). FakePay does not copy Stripe's check that "compares incoming parameters to those of the original request and errors if they're not the same".
   - `expiresAt` must be 30 minutes to 24 hours ahead: "It can be anywhere from 30 minutes to 24 hours after Checkout Session creation" ([Create a Checkout Session, `expires_at`](https://docs.stripe.com/api/checkout/sessions/create)). FakePay applies the range exactly (tests at 30 minutes minus one second, 30 minutes, 24 hours and 24 hours plus one second). Payments therefore asks for the session lifetime plus a margin (`Payments:Provider:ExpiryMargin`, 30 s), because "now + 30 minutes" is a moment short by the time the request arrives. The margin is our choice; we did not check how Stripe treats a request that is a moment short.
   - **Decline leaves the session open.** Stripe's card-declines page says: "Checkout provides feedback to the customer when a card declines and allows them to try again" ([Card declines, Reduce card declines](https://docs.stripe.com/declines/card)). No page we found states that the Checkout Session stays `open` after a decline, so this part is the owner's decision (README: "FakePay's Decline button leaves the payment open"), not a confirmed Stripe behaviour.
   - Webhooks are signed and retried until a `2xx`; Stripe: "Stripe attempts to deliver events to your destination for up to three days with an exponential back off in live mode" ([Event delivery behaviors](https://docs.stripe.com/webhooks#automatic-retries)). FakePay retries at a fixed interval, and can send each event twice (`FakePay:DeliverTwice`) to make duplicates easy to test.
4. **Webhook signing and the replay window follow Stripe's scheme.** The header is `FakePay-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(secret, "{t}.{body}")>`, which is Stripe's: the signed text is "the timestamp value (as a string), the character `.`, the actual JSON payload" and the HMAC uses SHA-256 ([Verify manually](https://docs.stripe.com/webhooks?verify=verify-manually#verify-manually)). Payments checks two things, in this order: the HMAC, compared in constant time, and then that the timestamp is within 5 minutes of now in either direction. The timestamp is inside the signed text, so "an attacker can't change the timestamp without invalidating the signature" ([Preventing replay attacks](https://docs.stripe.com/webhooks#preventing-replay-attacks)), which is why a signature alone would let a captured request be sent again next week. Stripe's libraries use the same 5-minute default. Our check reads one `v1` value. Stripe's page says: "You can have multiple signatures with the same scheme when you roll an endpoint's signing secret, and keep the previous secret active for up to 7 days. During this period, your endpoint has multiple active secrets and Stripe generates one signature for each secret. Verify that at least one `v1` entry is valid." ([Verify manually](https://docs.stripe.com/webhooks?verify=verify-manually#verify-manually)); the Stripe implementation must accept any matching one.
5. **The webhook handler is idempotent by a table and a guard,** in one transaction. First it inserts the provider's event id into `provider_events` (`ON CONFLICT DO NOTHING`); zero rows means a duplicate, so it answers 200 and changes nothing. Then it moves the payment out of `Created` only (`UPDATE … WHERE status = 'Created'`) and enqueues the event in the same transaction.
   - **Why the insert is safe under parallel deliveries.** PostgreSQL makes the second insert wait: "If a conflicting row has been inserted by an as-yet-uncommitted transaction, the would-be inserter must wait to see if that transaction commits. If it rolls back then there is no conflict. If it commits without deleting the conflicting row again, there is a uniqueness violation." ([PostgreSQL, Index Uniqueness Checks](https://www.postgresql.org/docs/current/index-unique-checks.html)). With `ON CONFLICT DO NOTHING` the violation becomes "no row". The test `Ten_parallel_deliveries_of_one_webhook_publish_once` runs it.
   - **Why two guards.** Stripe advises the first: "guard against duplicated event receipts by logging the event IDs you've processed, and then not processing already-logged events" ([Handle duplicate events](https://docs.stripe.com/webhooks#handle-duplicate-events)). The second answers "Stripe doesn't guarantee the delivery of events in the order that they're generated" ([Event ordering](https://docs.stripe.com/webhooks#event-ordering)): a late `expired` after a `completed` finds the payment out of `Created` and changes nothing.
6. **Creating a payment is safe to repeat.** The attempt is inserted first (`ON CONFLICT (order_id) DO NOTHING`, so parallel creates for one order insert one row and raise no error; the test `Parallel_creates_for_one_order_make_one_payment` sends 10 at once and sees one `201`, nine `200`, one row and one provider request), then the session is created with the attempt's id as the provider's idempotency key, then stored. If the provider call fails, the attempt stays without a session, the endpoint answers 503 `dependency-unavailable` with `Retry-After`, and the next call finishes it with the same key (`Provider_down_gives_503_and_a_retry_completes_the_same_payment`). The session call runs while a row lock (`SELECT … FOR UPDATE`) is held, so parallel callers wait and then find the session, and the provider sees one request.
   - **The lock needs a short pipeline.** The lock, the transaction and a pooled connection are held for the whole provider call, including its retries. With the standard resilience handler's defaults, which Microsoft documents as "Max retries: 3, Backoff: Exponential, Delay: 2s", a total timeout of 30 s and an attempt timeout of 10 s ([Standard resilience handler defaults](https://learn.microsoft.com/dotnet/core/resilience/http-resilience#standard-resilience-handler-defaults)), a provider that is down would keep them for about 14 s of backoff (2 + 4 + 8) and up to 30 s: longer than the caller's own 10 s attempt timeout, which is the same default for Orders' `AddServiceClient` client. So session creation has its own client (`FakePay-session`) with the same handler tuned by options: one retry after 200 ms (`SessionRetryDelay`), 2 s per attempt (`SessionAttemptTimeout`) and 5 s in all (`SessionTotalTimeout`). Startup validation rejects a total above 8 s. Orders retries a 503 anyway, and the repeat is safe, so failing fast costs nothing; holding the lock longer than the caller waits would only keep a connection busy for a call nobody is waiting for. The test `A_provider_that_never_answers_gives_503_within_the_session_budget_and_frees_the_lock` runs with the shipped options (the test fixture trims only the refund client) against a provider that never answers, and asserts a 503 with `Retry-After` in under 8 s and that the next call for the order does not wait.
   - Refunds keep the standard pipeline: they hold no lock, and the message that asked for them is retried without a limit.
7. **A refund is driven by an event.** Orders publishes `RefundRequested` (topic `orders.orders`); Payments' handler refunds with the payment id as the idempotency key, marks the attempt `Refunded` and enqueues `PaymentRefunded`. A provider that is down raises `HttpRequestException` (a 5xx) or `TransientFailureException`, which Messaging retries without a limit (ADR 0008, amended). A payment that is not `Succeeded` raises `InvalidOperationException`: the message is dead-lettered, because retrying cannot change the payment.
8. **Polly's rejections become `TransientFailureException` inside `FakePayProvider`.** Both provider clients use the standard resilience handler. Polly's circuit breaker "will throw either a BrokenCircuitException or an IsolatedCircuitException" when it is open or isolated ([Circuit breaker](https://www.pollydocs.org/strategies/circuit-breaker.html)), and "if the execution is canceled by the timeout strategy, it throws a `TimeoutRejectedException`" ([Timeout](https://www.pollydocs.org/strategies/timeout.html)). Messaging does not classify them (ruling from Task 1's review). Converting them in the client, which chose to add the pipeline, keeps Messaging free of Polly and makes a refund wait while FakePay's circuit is open. A test covers both exceptions on both calls.

## Alternatives considered

- **Payments as a module inside Orders.** Fewer deployables, but Orders would own both the saga and the provider's wire format and secrets, and the refund path could not be tested on its own. The owner chose a service; the cost is one more container and the two events.
- **No interface; call FakePay's client directly.** Less code today. Phase 7 would then touch the endpoint, the handler and the webhook code. With the interface only `FakePayProvider` is replaced.
- **Stripe test mode from the start.** Stripe's docs say that "Registered webhook endpoints must be publicly accessible HTTPS URLs", or that the Stripe CLI can forward events to a local listener ([Set up your endpoint](https://docs.stripe.com/webhooks#set-up-your-endpoint)). Either needs a network, an account and keys in every test run and in CI. FakePay keeps tests offline and lets them cause failures on demand (expiry, duplicates, a down receiver). The price is that FakePay can drift from Stripe; Phase 7's test-mode payment is what catches that.
- **A signature without a timestamp check.** Simpler, but a captured valid request would be accepted whenever it was sent. The event-id table stops a replay of an event we already handled, but it keeps every id for as long as we keep the table; the window limits what an old capture can do, and old ids can be pruned.
- **Refund by a synchronous call from Orders to Payments.** Orders would have to handle Payments being down at the moment it decides to refund. With the event, the decision is written to Orders' outbox with the order's change, and Payments acts when it can. The price is that Orders learns the result later, by `PaymentRefunded`.
- **Check "already handled" with a read before the write** (`SELECT` the event id, then act). Two deliveries at the same moment both pass the read. The insert with `ON CONFLICT DO NOTHING` is one atomic step: the second insert waits for the first transaction and then finds the key taken (the same mechanism as the inbox, `IdempotentDispatcher`).

## Consequences

- Orders (Task 7) consumes `PaymentSucceeded`, `PaymentFailed` and `PaymentRefunded` from `payments.payments` and publishes `RefundRequested` to `orders.orders`. A shared topic needs one place for its name and partition count, so each producer has a static class for it (`PaymentEvents`, `OrderEvents`); AGENTS.md says so.
- A webhook with a bad signature, a stale timestamp or a type FakePay never sends is refused with 400 (`IPaymentProvider.ReadWebhook` returns null for all three); an unknown type is logged at Warning. FakePay never sends another type. A Stripe implementation will see more types and needs a way to say "valid, ignore it" so that Stripe is answered 200.
- The anonymous webhook endpoint reads at most 16 KiB (`WebhookEndpoint`): a webhook is a few hundred bytes, and a larger body is refused with 413 before the signature check (`A_body_over_the_limit_is_refused_before_the_signature_is_checked`).
- A `completed` webhook for a payment that is already `Failed` moves nothing and is logged at Warning with the event and payment ids: the provider took money for a payment we gave up on, and a person must look. There is no automatic refund for it yet.
- `provider_events` grows by one row per webhook and has no cleanup yet.
- Creating a payment holds a row lock, a transaction and a pooled connection for at most `SessionTotalTimeout` (5 s by default, at most 8 s by validation) while it calls the provider; the budget is set in `FakePayProviderRegistration` and shown by the test in decision 6. At Orders' rate this is fine; a high-volume service would not hold the lock across a network call.
- FakePay's local credentials are set in `compose.yaml` and `appsettings.Development.json`, the places AGENTS.md allows; they are not repeated here.
