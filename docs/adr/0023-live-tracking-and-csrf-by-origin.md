# 0023. Live tracking: one SignalR hub, WebSockets only, a Redis backplane, and CSRF by Origin

## Status

Accepted

## Date

2026-11-26

## Context

The buyer watches the courier move on a map. The courier produces a position every 2 s (ADR 0022), Delivery's API role stores it, and the browser should see it at once, without polling. Delivery's API runs as two instances behind the gateway (`delivery` and `delivery-b`), both in one Kafka consumer group, so the instance that consumes a shipment's partition is often not the one that holds the buyer's connection.

Four forces shape the design:

- **SignalR and a server farm.** "SignalR requires the same server process handle all HTTP requests for a specific connection. When SignalR runs on a server farm (multiple servers), "sticky sessions" must be used", with three exceptions, one of which is "All clients are configured to use WebSockets **only** and the client configuration enables SkipNegotiation" ([SignalR hosting and scaling, Sticky sessions](https://learn.microsoft.com/aspnet/core/signalr/scale?view=aspnetcore-10.0#sticky-sessions)). And without a backplane, "When SignalR on one of the servers wants to send a message to all clients, the message only goes to the clients connected to that server" ([Scale out](https://learn.microsoft.com/aspnet/core/signalr/scale?view=aspnetcore-10.0#scale-out)).
- **Groups don't survive a reconnect.** "Group membership isn't preserved when a connection reconnects. The connection needs to rejoin the group when it's re-established." ([Manage users and groups in SignalR](https://learn.microsoft.com/aspnet/core/signalr/groups?view=aspnetcore-10.0#groups-in-signalr)).
- **A token expires under a live connection.** "If a token expires during the lifetime of a connection, by default the connection continues to work. … For connections to close when the authentication token expires, set the CloseOnAuthenticationExpiration option." ([SignalR authentication and authorization](https://learn.microsoft.com/aspnet/core/signalr/authn-and-authz?view=aspnetcore-10.0#authenticate-users-connecting-to-a-signalr-hub)). Keycloak's access tokens last minutes, so this happens on every trip.
- **The browser authenticates with the gateway's session cookie** (ADR 0015), and the gateway's CSRF defence is the `X-CSRF: 1` header. A browser can't put a header on a WebSocket: "browsers can't set custom headers, such as `Authorization`, on the WebSocket and Server-Sent Events APIs" ([Bearer token authentication](https://learn.microsoft.com/aspnet/core/signalr/authn-and-authz?view=aspnetcore-10.0#bearer-token-authentication)), and the same holds for `X-CSRF`. CORS doesn't help either: "The protections provided by CORS don't apply to WebSockets. Browsers do **not**: Perform CORS pre-flight requests" ([WebSocket origin restriction](https://learn.microsoft.com/aspnet/core/fundamentals/websockets?view=aspnetcore-10.0#websocket-origin-restriction)).

## Decision

- **One hub, `TrackingHub` at Delivery's `/hubs/tracking`, WebSockets only.** The server sets `HttpConnectionDispatcherOptions.Transports = HttpTransportType.WebSockets`, so a client that asks for another transport is refused (the test `Server_refuses_long_polling` shows the negotiate answer offers WebSockets alone). The browser client sets `skipNegotiation`, so one connection is one HTTP request, the upgrade, and the gateway's round robin needs no sticky sessions.
- **The Redis backplane.** With `ConnectionStrings:Redis` set, Delivery calls `AddStackExchangeRedis` with `AbortOnConnectFail = false` and `ChannelPrefix = "newstore-delivery"` ([Set up a Redis backplane](https://learn.microsoft.com/aspnet/core/signalr/redis-backplane?view=aspnetcore-10.0#set-up-a-redis-backplane): "If you don't assign different prefixes, a message sent from one app to all of its own clients will go to all clients of all apps that use the Redis server as a backplane"). A position stored by `delivery-b` reaches a browser on `delivery` through Redis. Without the setting Delivery logs a Warning at start and runs without a backplane (one instance, `dotnet run`).
- **Two instances behind the gateway, round robin, an active health check, no sticky sessions.** The gateway's `delivery` cluster lists `Services:Delivery:0` and `:1` with `LoadBalancingPolicy = RoundRobin` ("Select a destination by cycling through them in order", [YARP load balancing](https://learn.microsoft.com/aspnet/core/fundamentals/servers/yarp/load-balancing?view=aspnetcore-10.0)) and probes each one's `/health/ready` every `Gateway:DestinationHealthChecks:Interval` (5 s) with the `ConsecutiveFailures` policy, whose threshold defaults to 2 ([YARP destination health checks](https://learn.microsoft.com/aspnet/core/fundamentals/servers/yarp/dests-health-checks?view=aspnetcore-10.0#active-health-checks)). Once marked unhealthy, a stopped instance gets no new requests or connections. Until then there is a window of up to about threshold × interval plus a probe's 2 s timeout (about 10 to 12 s in Compose) in which round robin still sends some requests and upgrades to it, and YARP answers those with 502 (`ReportErrorAsync(... ForwarderError.Request, StatusCodes.Status502BadGateway)`, [`HttpForwarder.cs` v2.3.0, line 692](https://github.com/dotnet/yarp/blob/v2.3.0/src/ReverseProxy/Forwarder/HttpForwarder.cs#L692)); the page retries. YARP's optional passive health checks, which watch the proxied requests themselves, are the way to shrink that window ([Passive health checks](https://learn.microsoft.com/aspnet/core/fundamentals/servers/yarp/dests-health-checks?view=aspnetcore-10.0#passive-health-checks)); this design doesn't turn them on.
- **`Track` joins, then reads; `CloseOnAuthenticationExpiration`; track again after every reconnect.** `Track(shipmentId)` checks that the shipment is the caller's (else `HubException("not-found")`), joins group `shipment:{id}`, and returns the snapshot. The hub sets [`CloseOnAuthenticationExpiration`](https://learn.microsoft.com/dotnet/api/microsoft.aspnetcore.http.connections.httpconnectiondispatcheroptions.closeonauthenticationexpiration?view=aspnetcore-10.0) ("Authenticated connections whose token sets the ExpiresUtc value will be closed and allowed to reconnect when the token expires", with the remark "Closed connections will miss messages sent while closed"), so a connection ends when its token does. The page reconnects through the gateway, which refreshes the access token from the session, calls `Track` again, and merges the snapshot by `seq`.
- **The token in the upgrade's `Authorization` header, never in the query string.** The gateway's `AccessTokenTransform` turns the session into a bearer token on the upgrade as on any other request. The documentation describes exactly this: "A reverse proxy, such as YARP fronting a backend-for-frontend (BFF), can also add the `Authorization` header to the proxied WebSocket request, so the backend authenticates with the header instead of the query string" ([Bearer token authentication](https://learn.microsoft.com/aspnet/core/signalr/authn-and-authz?view=aspnetcore-10.0#bearer-token-authentication)). YARP then tunnels the socket: "Step 7-A: Check for a 101 upgrade response, this takes care of WebSockets as well as any other upgradeable protocol" ([YARP `HttpForwarder.cs`, v2.3.0](https://github.com/dotnet/yarp/blob/v2.3.0/src/ReverseProxy/Forwarder/HttpForwarder.cs#L257)).
- **CSRF for the hub's upgrade by Origin, at the gateway.** A cookie-authenticated `GET` under `/api/hubs/` with `Upgrade: websocket` and a `Connection` header that contains `Upgrade` passes when its `Origin` is one of `Gateway:PublicOrigins` (ordinal, ignoring case, without a trailing `/`), with or without `X-CSRF`; any other Origin, or none, is 403 `csrf`. Every other cookie request keeps the `X-CSRF` rule. The Origin can be trusted from a browser: "`Sec-Fetch-Site` and `Origin` are forbidden request headers: the browser sets them, and JavaScript running in a page can't override or forge them" ([Prevent CSRF attacks, Fetch metadata headers](https://learn.microsoft.com/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0#fetch-metadata-headers)). The gateway tells an upgrade by its headers because it has no WebSockets middleware, and only that middleware adds the feature behind `IsWebSocketRequest`: it "Enables accepting WebSocket requests by adding a IHttpWebSocketFeature to the HttpContext if the request is a valid WebSocket request" ([WebSocketMiddleware](https://learn.microsoft.com/dotnet/api/microsoft.aspnetcore.websockets.websocketmiddleware?view=aspnetcore-10.0)). `SameSite=Strict` (ADR 0015) stays as the second layer.

## Alternatives considered

- **Sticky sessions, with negotiate and the fallback transports.** The default client negotiates first and may fall back to Server-Sent Events or long polling; then every request of a connection must reach one process, "including when the Redis backplane is used" ([Sticky sessions](https://learn.microsoft.com/aspnet/core/signalr/scale?view=aspnetcore-10.0#sticky-sessions)). YARP can do it with [session affinity](https://learn.microsoft.com/aspnet/core/fundamentals/servers/yarp/session-affinity?view=aspnetcore-10.0), which is one more policy to configure and test in the gateway. WebSockets only removes the need, at the price below.
- **Long polling or SSE as a fallback.** It serves a network that blocks WebSockets. It brings back negotiate and with it sticky sessions, and those transports make a request per poll or per send: "`LongPolling` and `ServerSentEvents` connections fail on subsequent requests if they don't send new access tokens" ([SignalR authentication and authorization](https://learn.microsoft.com/aspnet/core/signalr/authn-and-authz?view=aspnetcore-10.0#authenticate-users-connecting-to-a-signalr-hub)). The app's users are on current browsers and the gateway is ours, so the fallback buys little here.
- **The token in the `access_token` query string.** This is what the browser client does without a proxy, and "many servers log query string values" ([Bearer token authentication](https://learn.microsoft.com/aspnet/core/signalr/authn-and-authz?view=aspnetcore-10.0#bearer-token-authentication)). It would also put the access token in the browser, which ADR 0015 keeps on the server.
- **`UseWebSockets` with `WebSocketOptions.AllowedOrigins`.** ASP.NET Core's own Origin check, in Delivery or in the gateway: "A list of allowed Origin header values for WebSocket requests. By default, all origins are allowed." ([Configure the middleware](https://learn.microsoft.com/aspnet/core/fundamentals/websockets?view=aspnetcore-10.0#configure-the-middleware)). It lets a request without an `Origin` through: it compares only when the header is present (`if (!StringValues.IsNullOrEmpty(originHeader) && webSocketFeature.IsWebSocketRequest)`, then `StringComparer.Ordinal`, [`WebSocketMiddleware.cs` at v10.0.15](https://github.com/dotnet/aspnetcore/blob/v10.0.15/src/Middleware/WebSockets/src/WebSocketMiddleware.cs#L65-L73)). A cookie-authenticated upgrade with no Origin is one this design refuses. In the gateway it would also add a middleware that YARP doesn't need for the tunnel. The check in `CsrfMiddleware` sits next to the rule it replaces and applies to exactly the requests that rule covers: cookie-authenticated ones.
- **Checking the Origin in Delivery instead of at the front door.** Delivery sees only the bearer token the gateway made; the cookie, which is what a hostile page abuses, never reaches it. The decision belongs where the cookie is turned into a token. Delivery also serves bearer clients (tests, tools) that have no Origin at all.

## Consequences

- **No fallback for a network that blocks WebSockets.** Such a buyer sees the shipment page with its snapshot and status, refreshed on reload, but no live movement.
- **A connection lives at most as long as one access token,** and the page reconnects about that often. JwtBearer sets the ticket's expiry to the token's own (`ExpiresUtc = ValidTo`, [`JwtBearerHandler.cs`](https://github.com/dotnet/aspnetcore/blob/v10.0.15/src/Security/Authentication/JwtBearer/src/JwtBearerHandler.cs#L159)), without the validation's `ClockSkew`, so the close comes on time (`Connection_closes_when_the_token_expires`). Positions sent during the gap are not delivered; the snapshot on the next `Track` has them, and the client drops repeats by `seq`.
- **A broadcast sent while Redis is down is lost.** "SignalR doesn't buffer messages to send them when the server comes back up. Any messages sent while the Redis server is down are lost." ([Redis server errors](https://learn.microsoft.com/aspnet/core/signalr/redis-backplane?view=aspnetcore-10.0#redis-server-errors)). The handler logs a failed send and keeps the stored rows, so the next snapshot covers it. New connections fail too, not only broadcasts: with the backplane a connection subscribes to its own channels in Redis when it opens, and the test `While_redis_is_down_a_new_connection_is_closed_and_track_fails` measured the result: the handshake completes, then the server closes the connection with an error about 5 s later and the pending `Track` fails ("Websocket closed with error: InternalServerError."). The page treats that like any dropped connection and retries until Redis is back (Task 6).
- **Origin is a browser defence, not authentication.** "The `Origin` header is controlled by the client and, like the `Referer` header, can be faked. Do **not** use these headers as an authentication mechanism." ([WebSocket origin restriction](https://learn.microsoft.com/aspnet/core/fundamentals/websockets?view=aspnetcore-10.0#websocket-origin-restriction)). A script outside a browser can send any Origin, but it has no victim's cookie to send with it; the session cookie and the route's signed-in policy stay the authentication.
- **The check and the route know HTTP/1.1's upgrade only.** "HTTP/2 WebSockets use CONNECT requests rather than GET" ([HTTP/2 WebSockets support](https://learn.microsoft.com/aspnet/core/fundamentals/websockets?view=aspnetcore-10.0#http2-websockets-support)), and the `hubs-tracking` route and `IsHubUpgrade` accept `GET`. The gateway serves plain HTTP until Phase 4; when HTTPS arrives, the upgrade either stays on HTTP/1.1 at the gateway or both learn the CONNECT form.
- **`Gateway:PublicOrigins` must list every origin the app is served from,** or live tracking fails there with 403. Compose lists `http://localhost:8100` and `http://localhost:4200` (`npm start`).
